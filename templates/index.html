Beginner Mode -- Learn PPCL Basics

A quick primer on the PPCL syntax this trainer uses, before you dive into Beginner, Intermediate, or Expert scenarios. You don't need to memorize this -- come back any time.

1. What is PPCL?

PPCL (Powers Process Control Language) is the line-numbered programming language used on Siemens APOGEE field panels to write building automation control sequences -- things like "if the room is too warm, open the cooling valve." Programs run top-to-bottom, once per scan cycle, over and over, continuously checking conditions and updating outputs.

2. Line Numbers

Every statement starts with a line number, traditionally in steps of 10 (01000, 01010, 01020...) so you can insert a new line later without renumbering everything. This editor auto-numbers for you, starting at 01000.

01000 "%X%CT01.FAN.ENA" = ON 01010 "%X%CT01.FAN.SPD" = 55

3. Points -- the things you read and control

A "point" is a single value in the field panel's database -- a sensor reading, a command output, or an internal calculated value. Point names are always quoted strings following the pattern "%X%SYSTEM.SUBPOINT", e.g. "%X%EF01.EF.RUN" (EF01's Exhaust Fan Run Output). The Program Editor tab shows you exactly which points a scenario expects you to use.

3a. Point Type Reference

Every point also has a type code (LAI, LDO, L2SL...) describing what kind of I/O it wires to in the field. Click a type below to see it used in a real scenario.

4. IF / THEN / ELSE

The core building block. The condition must be wrapped in parentheses. ELSE is optional but usually needed so the output goes back to its normal state when the condition stops being true.

01000 IF ("%X%MAU01.DAT" .GT. "%X%MAU01.DAT.HI") THEN ON ("%X%MAU01.DAT.ALM") ELSE OFF ("%X%MAU01.DAT.ALM")

5. Comparison Operators

.EQ. equal, .NE. not equal, .GT. greater than, .LT. less than, .GE. greater or equal, .LE. less or equal, .AND. / .OR. to combine conditions. They always sit between two values, surrounded by dots. The Siemens manual caps any single statement at a combined total of 16 relational + logical operators.

5a. Two More Logical Operators -- .NAND. / .XOR.

.XOR. is true when exactly one of the two conditions is true (not both, not neither) -- handy for "these two should never agree" checks like two lead-lag pumps both claiming to be running.

200 IF ("%X%CHWP01.ENA" .XOR. "%X%CHWP02.ENA") THEN OFF ("%X%CHWP.ALM") ELSE ON ("%X%CHWP.ALM")

.NAND. exists too, but it's worth flagging a real gotcha rather than teaching it as a fixed rule: its truth table actually changed between Siemens firmware revisions (older logical-panel firmware evaluated it one way, rev 9.1+/CM/APOGEE firmware evaluates it differently). Since which one you're running depends on the panel in front of you, treat any .NAND. you find in an existing program as something to verify against that specific panel's firmware rather than assume.

5b. Arithmetic Operators & Order of Operations

Basic math uses + - * / the way you'd expect (max 15 arithmetic operators per line), but PPCL evaluates a mixed expression in a fixed order, high to low precedence: parentheses first, then built-in functions (Section 5c below), then the .ROOT. operator, then multiplication/division, then addition/subtraction, then comparisons (.EQ./.GT./...), then .AND./.NAND., then .OR./.XOR. last. Operators at the same level evaluate left to right.

"%X%CT01.RESULT" = 10 - 5 + 2 * 3 "%X%CT01.RESULT" = (10 - 5 + 2) * 3

The first line evaluates to 11 (multiplication happens before the subtraction/addition around it); the second evaluates to 21 (the parentheses force the addition/subtraction to happen first, then the whole result gets multiplied by 3). One real gotcha worth knowing even though this trainer's point names are always quoted: never name a point (or assign to) a bare C -- a line starting with an unquoted C is read by the panel as a comment, not code, so 500 C = OATEMP silently does nothing.

5c. Math & Trig Functions

PPCL has a small built-in math library, usable anywhere a value is expected. All trig functions work in degrees, not radians: SQRT(v) square root, SIN(v) / COS(v) / TAN(v) trig functions, ATN(v) arc-tangent (returns degrees), LOG(v) natural log, EXP(v) natural antilog (e^v), COM(v) one's complement (flips a digital 0/1 to its opposite), and the .ROOT. operator for arbitrary roots: value.ROOT.n is the n-th root of value.

"%X%CT01.RVAL" = ("%X%CT01.TEMP" .ROOT. 3.0) "%X%CT01.PWR" = "%X%CT01.V" * "%X%CT01.I" * COS("%X%CT01.THETA")

The first line takes the cube root of TEMP; the second is a real-power calculation from volts, amps, and phase angle -- the kind of math you'd see feeding an energy-monitoring point off a power meter's raw readings.

6. ON() / OFF() / SET() -- commands vs. values

ON/OFF/SET are commands only when immediately followed by parentheses, e.g. ON("%X%PT") or SET(55,"%X%PT"). Written bare (no parentheses), ON/OFF are just values you compare against, e.g. IF ("%X%FCU101.CLG.VLV" .EQ. ON) THEN ... checks whether a point's current value already equals ON -- it doesn't turn anything on.

7. SAMPLE(n) -- timers and accumulators

SAMPLE(n) makes something only execute once every n seconds instead of every scan cycle -- the standard way to build a timer or delay. It can gate just the action inside a THEN clause:

01000 IF ("%X%MAU01.SF.SS" .EQ. ON .AND. "%X%MAU01.SF.S" .EQ. OFF) THEN SAMPLE(1) "%X%MAU01.SF.ALM.TMR" = "%X%MAU01.SF.ALM.TMR" + 1 01010 IF ("%X%MAU01.SF.ALM.TMR" .GT. 30) THEN ON ("%X%MAU01.SF.ALM")

Or it can gate an entire IF statement placed right after it -- real field panel dumps use this form just as often, especially inside a GOTO-dispatched alarm block. Here the whole condition check, not just the action, only runs once every N seconds:

01000 SAMPLE(1) IF ("%X%AHU02.DAT" .GT. "%X%AHU02.DAT.HI") THEN "%X%AHU02.DAT.ALM.TMR" = "%X%AHU02.DAT.ALM.TMR" + 1

Both forms are valid PPCL and this trainer's simulator runs either one correctly -- use whichever reads more naturally for the sequence you're writing.

8. GOSUB / RETURN -- subroutines

GOSUB jumps execution to another line number and runs until it hits RETURN, then comes back to right after the GOSUB call. Handy for logic reused in several places in one program.

01000 GOSUB 1100 ... 01100 C ---- SUBROUTINE ---- 01110 IF ("%X%EF01.LVR.POS" .EQ. OFF) THEN ON ("%X%EF01.EF.ALM") 01120 RETURN

Two rules from the Siemens manual worth knowing: don't pair GOSUB directly with an IF/THEN/ELSE (call it from a plain line instead), and don't put another timed command -- LOOP, SAMPLE, TOD, WAIT -- inside the subroutine body itself. The last line of a subroutine must always be RETURN.

8a. GOTO -- decision-tree dispatch

GOTO permanently redirects execution to another line number -- unlike GOSUB, it never comes back. Real Siemens AHU programs lean on this constantly: at the very top of the program, a short block checks safety trips first (smoke detectors, freeze stats, high static), unconditionally overriding everything else, then checks which operating mode is active and jumps to that mode's block. Safety is always checked before mode, never after -- a real fault has to win regardless of what the schedule says.

01000 IF ("%X%AHU01.SSD" .EQ. ON) THEN GOTO 02000 01010 IF ("%X%BLDG.OCC.STATE" .EQ. 0) THEN GOTO 01100 01020 IF ("%X%BLDG.OCC.STATE" .EQ. 1) THEN GOTO 01200 01100 C --- OCCUPIED BLOCK --- 01110 ON ("%X%AHU01.SF.ENA") 01120 GOTO 03000 01200 C --- UNOCCUPIED BLOCK --- 01210 OFF ("%X%AHU01.SF.ENA") 01220 GOTO 03000 02000 C --- SAFETY BLOCK --- 02010 OFF ("%X%AHU01.SF.ENA") 02020 GOTO 03000 03000 C --- END OF SCAN ---

Notice every GOTO target is a line number higher than the line it's jumping from -- the Safety check at line 01000 jumps forward to the Safety block at 02000, and every block (Occupied, Unoccupied, and Safety) ends with its own GOTO 03000 forward to the shared landing line, which sits last in the program since it has the highest number. That's not just a style choice: without it, finishing the Occupied block would fall straight through into whatever comes next in the file (here, the Safety block), silently undoing what the block just did. Every dispatched section needs its own way out. The Siemens manual's actual wording on this is narrower than a flat "never jump backward" -- what it warns against is using GOTO to jump back without first executing the program's last line that pass, since that line is also the power-fail recovery point and skipping it risks an infinite loop that never reaches the end of the scan. In practice, forward-only is the safe convention real programs follow (and the one this trainer's simulator enforces), so treat it as the rule to write by.

8b. LOOP -- PID control loops

LOOP drives a modulating output (a valve, a VFD speed signal) to hold an analog process variable at a setpoint -- the software version of a PID controller. It always takes exactly 12 positional arguments, in this fixed order:

LOOP(type, pv, cv, sp, pg, ig, dg, st, bias, lo, hi, 0)

type is 0 (direct acting -- output rises as the process variable rises) or 128 (reverse acting -- output rises as the process variable falls, e.g. a pump speeding up as pressure drops). pv is the point being measured, cv the output point being driven, sp the setpoint. pg/ig/ dg are the proportional, integral, and derivative gains (set unused gains to 0). st is the sample time in seconds (minimum 1). bias is the output value when the process variable exactly equals setpoint in a proportional-only loop. lo/hi are the output's low and high limits, and the trailing 0 is always present but unused.

2018 LOOP(0,RM100,HVALVE,HSETPT,PGAIN,0,0,1,5.5,3.0,9.0,0)

That official example drives a heating valve (HVALVE, output range 3.0-9.0) to hold room temperature (RM100) at setpoint (HSETPT) with proportional gain only (PGAIN) and no integral/derivative action, sampled every 1 second, biased to 5.5 at the valve's midpoint.

9. $LOC / $ARG -- local variables

$LOC and $ARG (optionally numbered, e.g. $LOC1) are scratch variables local to the program -- useful for temporary math or holding a value partway through a calculation, without needing a permanent database point for it. Every new program comes with 15 of each built in automatically: $LOC1-$LOC15 for general calculation results, and $ARG1-$ARG15 specifically for passing values into and out of subroutines. Local variables use less memory than a real point, but the tradeoff is they can't be displayed directly on a graphic or commanded from the Commander application -- they only exist inside the program(s) that use them.

9a. LOCAL() -- creating your own named local variables

Need more scratch variables than the built-in 15, or want one with a meaningful name instead of a number? LOCAL(pt1...pt16) declares up to 16 custom local variables in one line -- once declared, they behave exactly like $LOC1-$LOC15 do.

01000 LOCAL (VIR1, VIR2, VIR3, VIR4, VIR5)

Whether built-in or custom, a local variable's name must always be preceded by a $ when you actually use it in a statement, so the panel knows it's a local variable and not a system/database point:

01010 ON ($VIR1)

Local variables are normally scoped to the program that declared them, but another program in the same field panel can still read one by prefixing it with that program's name and a colon:

01020 IF ("PROG1:FANPT" .EQ. ON) THEN ...

10. DEFINE -- reusing one block of code across devices

Syntax: DEFINE(abbrev,string). abbrev is a short placeholder; string is the text (typically a long point-name prefix) it stands in for. Wherever you use the placeholder later in the program, it must be written surrounded by percent signs -- %abbrev% -- so PPCL knows to substitute it. This lets five identical AHUs share one block of control logic: rather than writing (or copy-pasting) five near-duplicate programs that differ only in their point names, each device's copy of the program carries its own DEFINE line mapping the same placeholder to that unit's real point prefix, and the logic below it stays identical.

01000 DEFINE(AHU,"BUILDING1.AHU01.") 01010 ON ("%AHU%SFAN")

Line 01010 is equivalent to writing ON ("BUILDING1.AHU01.SFAN") directly -- DEFINE runs once when the program is loaded onto the controller (it isn't part of normal line-by-line execution), and an abbreviation that starts with the letter C will fail to compile since a leading C marks a comment line. This trainer's scenarios don't require DEFINE -- every point name is spelled out in full so a scenario stays self-contained and checkable -- but it's worth knowing about since real multi-unit PPCL programs lean on it heavily to avoid maintaining the same logic in five different places.

11. Comments

A line starting with a bare C token is a comment -- often used as a header or label above a block of related logic, and completely ignored by the panel at runtime. Real PPCL programs typically open with one comment naming the whole program, then a comment ahead of each logical section.

01000 C --- CHLR CHILLER PLANT CONTROL PROGRAM --- 01010 C --- LEAD-LAG ROTATION LOGIC ---

12. Special Functions -- ALMPRI() and TOTAL()

ALMPRI(pt) returns a point's current alarm priority level (1-6, under enhanced alarming) -- test it directly in an IF, or assign it to another point to log it. TOTAL(pt) returns a point's totalized runtime accumulation value. Both have one real restriction worth knowing before you reach for them: the target point has to live in the same field panel as the program calling them -- neither works across the network on a point that belongs to another panel.

240 IF (ALMPRI("%X%CHLR.LEAD.FLT") .EQ. 1) THEN ON ("%X%OPBELL") 810 IF (TOTAL("%X%CT01.FAN.ENA") .GT. 500.0) THEN ON ("%X%CT01.FAN.MAINT")

13. Resident Points -- built-in values you can read anywhere

The panel maintains a set of system-level points every program can read without declaring or writing to them -- useful for scheduling and diagnostics logic instead of building your own from scratch:

TIME -- current time in military format (0:00-23:59); can't be assigned to a virtual point since it isn't decimal. CRTIME -- the same clock as a decimal (0.00-23.999, so 7:15am = 7.25) -- use this one if you want to display or trend time-of-day on a graphic. DAY -- day of week, 1=Monday...7=Sunday. DAYOFM -- day of month, 1-31. MONTH -- 1=January...12=December. $BATT -- backup battery strength (0/50/100, or DEAD/LOW/OK). LINK -- 1 if the panel is currently communicating, 0 if not. NODE0-NODE99 -- status of a specific network node by address. SECNDS (and SECND1-SECND7 for seven independent ones) -- a free-running seconds counter/timer you can read, set, or reset from PPCL, capped at 9,999. ALMCNT -- live count of points in this panel currently in alarm.

100 IF (TIME .GE. 6:45 .AND. TIME .LE. 17:30) THEN ON ("%X%AHU01.SF.ENA") ELSE OFF ("%X%AHU01.SF.ENA") 110 IF ($BATT .EQ. DEAD) THEN ON ("%X%PNL.BATT.ALM")

14. Priority Indicators -- @EMER / @OPER / @SMOKE / @PDL / @NONE

Every point actually holds a small priority array under the hood, not just one value -- this is how a smoke-alarm shutdown can override a technician's manual command without erasing it. An @priority keyword lets you test, command, or release a point at a specific level: @EMER (the default when no priority is given), @SMOKE, @OPER, @PDL (demand-limiting), or @NONE.

300 IF ("%X%AHU01.SF.SS" .EQ. @EMER) THEN ON ("%X%HORN") 500 ON (@EMER,"%X%AHU01.SF.SS") 700 RELEAS (@EMER,"%X%AHU01.SF.SS")

Two gotchas: including an @priority keyword takes up the first parameter slot in ON/OFF/RELEAS/SET, which normally allow up to 16 points, so it drops the max to 15. And RELEAS only releases a point sitting at that priority or lower -- releasing at @EMER won't touch a point currently locked at @SMOKE, which matches how it should work in the field: a lower authority can't override a safety trip.

15. Point Status Keywords -- beyond ON/OFF

ON/OFF aren't the only bare status values PPCL understands -- several more exist for specific point types, used the same way: IF (pt .EQ. STATUS) THEN.... ALARM -- point is currently in alarm. ALMACK -- point's alarm has been acknowledged by an operator. FAILED -- point is in a failed state. HAND -- point is under manual switch control at a Point Termination Module. AUTO -- an analog loop point is in automatic (vs. manual) mode. PRFON -- proof-of-operation is currently ON. DAYMOD / NGTMOD -- an equipment controller is in occupied/unoccupied mode.

400 IF ("%X%CHLR1.ENA" .EQ. HAND) THEN ON ("%X%CHLR1.OVRD.ALM")

16. Program Size & Naming Rules

Line numbers can run from 1 to 32,767 -- this trainer's fixed 5-digit auto-numbering starting at 01000 is a formatting convention for consistency, not a hard panel limit. Programs execute in ascending line-number order and then wrap back to the first line automatically; that first line should always be reachable every single pass, since it also doubles as the recovery point the panel resumes at after a power failure. Point names longer than 6 characters, or containing anything other than letters/digits, must be double-quoted -- which is exactly why every point name in this trainer is quoted, and why a real point reads "BUILDING1.AHU01.SFAN" rather than a bare word.

17. MIN() -- lowest value of a group

Selects the smallest value out of 2-15 points or numbers and stores it in a result point: MIN(RESULT, PT1, PT2, PT3...). Useful for finding the lowest reading in a group of related devices -- e.g. the coldest room in a zone.

MIN (AO1, AI1, AI2, AI3, AI4)

If AI1=5, AI2=6, AI3=7, and AI4=10, AO1 gets set to 5 -- the smallest of the four.

18. MAX() -- highest value of a group

The mirror image of MIN: selects the largest value out of 2-15 points or numbers and stores it in a result point: MAX(RESULT, PT1, PT2, PT3...). Useful for things like finding which VAV box in a group has its damper open the most.

MAX (AO1, AI1, AI2, AI3, AI4)

Same four values (AI1=5, AI2=6, AI3=7, AI4=10) -- this time AO1 gets set to 10, the largest.

19. DBSWIT() -- the software version of a mechanical thermostat

Syntax: DBSWIT(TYPE, INPUT, LOW, HIGH, pt1...pt12). TYPE is 0 for cooling mode (turns the listed points ON when the input rises above the high limit, OFF when it drops below the low limit) or 1 for heating mode (ON when input falls below the low limit, OFF when it rises above the high limit). Between the low and high limits the points hold their last state -- that gap is the dead band, which is what keeps equipment from short-cycling right at the setpoint.

DBSWIT (0, RMT, 72, 74, COMP, CFM, EFM) DBSWIT (1, RMT, 68, 70, HWP, HWV)

First line: cooling -- turn COMP/CFM/EFM ON once Room Temp rises above 74, OFF once it drops below a 2-degree dead band (72). Second line: heating -- turn HWP/HWV ON once Room Temp falls below 68, OFF once it rises above a 2-degree dead band (70).

20. TIMAVG() -- smoothing out a noisy reading

Syntax: TIMAVG(RESULT, sample time, # samples, INPUT). Takes a rolling average of an input over time instead of reacting to every single scan -- exactly what you want on a point that constantly jitters (a CFM/flow meter is the classic example), since reacting to every tiny fluctuation wastes network bandwidth and makes control hunt. Three rules: sample time must be a whole number (10 is valid, 10.5 is not); # samples must be an integer from 2 to 10; and the input must be an LAI/LAO point or a local variable.

TIMAVG ("CWF.AVG", 10, 5, GPM)

That takes one sample every 10 seconds and averages the 5 most recent ones. If the last 5 GPM readings were 1370, 1248, 1302, 1321, and 1296, CWF.AVG = their sum (6537) divided by 5 = 1307.4.

21. TABLE() -- linear reset curves and staged control

Watches an input point (X) and drives an output point (Y) along a straight-line path between coordinate pairs you define -- the standard way to build a temperature reset schedule or split one virtual signal across several staged devices. Syntax: TABLE(INPUT, OUTPUT, X1, Y1, X2, Y2...), up to 7 X/Y pairs, and the X values must always be listed in ascending order.

TABLE (AI1, AO1, 0, 0, 5, 50, 10, 100)

When AI1 is 0, AO1 is 0; when AI1 is 5, AO1 is 50 (the midpoint); when AI1 is 10, AO1 is 100 -- and every value in between rises in a straight line.

A real reset curve usually needs more than two points, since the relationship isn't one straight line end to end -- up to 7 X/Y pairs let you bend the curve at each breakpoint. Say a supply air setpoint (SAS) needs to reset off room temp (RMT) like this: RMT 60 -> SAS 75, RMT 65 -> SAS 68, RMT 68-72 -> SAS holds flat at 55, RMT 75 -> SAS 52, RMT 80 -> SAS 50 -- as the room gets warmer, less heat is needed so the setpoint falls, with a flat dead zone between 68-72 where it doesn't change at all:

TABLE (RMT, SAS, 60, 75, 65, 68, 68, 55, 72, 55, 75, 52, 80, 50)

Six X/Y pairs, X (RMT) ascending the whole way as required. The repeated Y value at 68 and 72 is what creates that flat dead-zone segment in the middle of the curve -- TABLE doesn't require each segment to actually slope, two consecutive points with the same Y just hold the output level across that stretch of input.

This same tool handles staged control too, not just curves: three separate TABLE statements sharing one virtual driver point can sequence a heating valve, a mixed air damper, and a cooling valve one after another as the virtual point sweeps from 0 to 100%, each occupying its own slice of the range -- e.g. TABLE (VIR, HCO, 0, 100, 33.3, 0) fully opens the heating valve at 0% and fully closes it by 33.3%, then a second TABLE statement takes over the mixed air damper through the middle of the range, and a third opens the cooling valve over the last third -- so one virtual point drives all three devices in sequence without any overlap.

21a. CSAL & Modular Programming -- one standard layout for every program

The current Siemens standard for writing PPCL is to pull a proven program from the Navigator Library -- called CSAL, the Custom Solutions Application Library -- and modify it to fit the job, rather than writing every program from a blank line 1. CSAL programs share a common, companywide layout, which pays off in three ways: troubleshooting is faster because every tech knows where to look, programs are tested and proven over time instead of reinvented per job, and a program written for one air handler can usually be reused on the next one with minimal changes.

That shared layout is called modular programming: instead of splitting the work across multiple program files, one AHU program's line numbers are organized into named functional blocks called operational modes, each living in its own reserved range of line numbers. The modes never connect to one another directly -- the only thing that routes between them is the Decision Tree block, which runs on every scan and GOTOs the program into whichever mode block applies right now. The standard AHU line-number layout looks like this:

LinesSection
01000-01900Common Area -- runs every pass, no matter the mode
02000-02900Decision Tree -- picks the mode/safety block to jump to
03000-03900Warm-Up
04000-04900Cool-Down
05000-05900Occupied
06000-06390Unoccupied
06400-06590Night Heating
06600-06990Night Cooling
07000-07190Safety SMK (smoke)
07200-07390Safety HSP (high static)
07400-07590Safety LTD (low temp)
08000-08400Humidity Control (only if the sequence calls for it)
08500-08900Fan Tracking (only if the unit modulates fan speed)
09000-09900Branch Specific -- special functions unique to this unit
10000End of Program -- GOTOs back to line 1

Not every unit uses every section -- a constant-volume AHU with no humidity control just skips the Humidity Control block entirely, and the Decision Tree never routes into it. The Common Area and Decision Tree are the only two blocks every program has, since they run regardless of mode; everything else is mode-specific and reached only through a GOTO from the Decision Tree.
