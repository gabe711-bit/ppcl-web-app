Beginner Mode -- Learn PPCL Basics

A quick primer on the PPCL syntax this trainer uses, before you dive into Beginner, Intermediate, or Expert scenarios. You don't need to memorize this -- come back any time.

1. What is PPCL?

PPCL (Powers Process Control Language) is the line-numbered programming language used on Siemens APOGEE field panels to write building automation control sequences -- things like "if the room is too warm, open the cooling valve." Programs run top-to-bottom, once per scan cycle, over and over, continuously checking conditions and updating outputs.

2. Line Numbers

Every statement starts with a line number, traditionally in steps of 10 (01000, 01010, 01020...) so you can insert a new line later without renumbering everything. This editor auto-numbers for you, starting at 01000.

01000 "%X%CT01.FAN.ENA" = ON 01010 "%X%CT01.FAN.SPD" = 55

3. Points -- the things you read and control

A "point" is a single value in the field panel's database -- a sensor reading, a command output, or an internal calculated value. Point names are always quoted strings following the pattern "%X%SYSTEM.SUBPOINT", e.g. "%X%EF01.EF.RUN" (EF01's Exhaust Fan Run Output). The Program Editor tab shows you exactly which points a scenario expects you to use.

3a. Point Type Reference

Every point also has a type code (LAI, LDO, L2SL...) describing what kind of I/O it wires to in the field. Click a type below to see it used in a real scenario.

4. IF / THEN / ELSE

The core building block. The condition must be wrapped in parentheses. ELSE is optional but usually needed so the output goes back to its normal state when the condition stops being true.

01000 IF ("%X%MAU01.DAT" .GT. "%X%MAU01.DAT.HI") THEN ON ("%X%MAU01.DAT.ALM") ELSE OFF ("%X%MAU01.DAT.ALM")

5. Comparison Operators

.EQ. equal, .NE. not equal, .GT. greater than, .LT. less than, .GE. greater or equal, .LE. less or equal, .AND. / .OR. to combine conditions. They always sit between two values, surrounded by dots.

6. ON() / OFF() / SET() -- commands vs. values

ON/OFF/SET are commands only when immediately followed by parentheses, e.g. ON("%X%PT") or SET(55,"%X%PT"). Written bare (no parentheses), ON/OFF are just values you compare against, e.g. IF ("%X%FCU101.CLG.VLV" .EQ. ON) THEN ... checks whether a point's current value already equals ON -- it doesn't turn anything on.

7. SAMPLE(n) -- timers and accumulators

SAMPLE(n) makes something only execute once every n seconds instead of every scan cycle -- the standard way to build a timer or delay. It can gate just the action inside a THEN clause:

01000 IF ("%X%MAU01.SF.SS" .EQ. ON .AND. "%X%MAU01.SF.S" .EQ. OFF) THEN SAMPLE(1) "%X%MAU01.SF.ALM.TMR" = "%X%MAU01.SF.ALM.TMR" + 1 01010 IF ("%X%MAU01.SF.ALM.TMR" .GT. 30) THEN ON ("%X%MAU01.SF.ALM")

Or it can gate an entire IF statement placed right after it -- real field panel dumps use this form just as often, especially inside a GOTO-dispatched alarm block. Here the whole condition check, not just the action, only runs once every N seconds:

01000 SAMPLE(1) IF ("%X%AHU02.DAT" .GT. "%X%AHU02.DAT.HI") THEN "%X%AHU02.DAT.ALM.TMR" = "%X%AHU02.DAT.ALM.TMR" + 1

Both forms are valid PPCL and this trainer's simulator runs either one correctly -- use whichever reads more naturally for the sequence you're writing.

8. GOSUB / RETURN -- subroutines

GOSUB jumps execution to another line number and runs until it hits RETURN, then comes back to right after the GOSUB call. Handy for logic reused in several places in one program.

01000 GOSUB 1100 ... 01100 C ---- SUBROUTINE ---- 01110 IF ("%X%EF01.LVR.POS" .EQ. OFF) THEN ON ("%X%EF01.EF.ALM") 01120 RETURN

Two rules from the Siemens manual worth knowing: don't pair GOSUB directly with an IF/THEN/ELSE (call it from a plain line instead), and don't put another timed command -- LOOP, SAMPLE, TOD, WAIT -- inside the subroutine body itself. The last line of a subroutine must always be RETURN.

8a. GOTO -- decision-tree dispatch

GOTO permanently redirects execution to another line number -- unlike GOSUB, it never comes back. Real Siemens AHU programs lean on this constantly: at the very top of the program, a short block checks safety trips first (smoke detectors, freeze stats, high static), unconditionally overriding everything else, then checks which operating mode is active and jumps to that mode's block. Safety is always checked before mode, never after -- a real fault has to win regardless of what the schedule says.

01000 IF ("%X%AHU01.SSD" .EQ. ON) THEN GOTO 02000 01010 IF ("%X%BLDG.OCC.STATE" .EQ. 0) THEN GOTO 01100 01020 IF ("%X%BLDG.OCC.STATE" .EQ. 1) THEN GOTO 01200 01100 C --- OCCUPIED BLOCK --- 01110 ON ("%X%AHU01.SF.ENA") 01120 GOTO 03000 01200 C --- UNOCCUPIED BLOCK --- 01210 OFF ("%X%AHU01.SF.ENA") 01220 GOTO 03000 02000 C --- SAFETY BLOCK --- 02010 OFF ("%X%AHU01.SF.ENA") 02020 GOTO 03000 03000 C --- END OF SCAN ---

Notice every GOTO target is a line number higher than the line it's jumping from -- the Safety check at line 01000 jumps forward to the Safety block at 02000, and every block (Occupied, Unoccupied, and Safety) ends with its own GOTO 03000 forward to the shared landing line, which sits last in the program since it has the highest number. That's not a style choice: without it, finishing the Occupied block would fall straight through into whatever comes next in the file (here, the Safety block), silently undoing what the block just did. Every dispatched section needs its own way out, and every jump has to move forward.

8b. LOOP -- PID control loops

LOOP drives a modulating output (a valve, a VFD speed signal) to hold an analog process variable at a setpoint -- the software version of a PID controller. It always takes exactly 12 positional arguments, in this fixed order:

LOOP(type, pv, cv, sp, pg, ig, dg, st, bias, lo, hi, 0)

type is 0 (direct acting -- output rises as the process variable rises) or 128 (reverse acting -- output rises as the process variable falls, e.g. a pump speeding up as pressure drops). pv is the point being measured, cv the output point being driven, sp the setpoint. pg/ig/ dg are the proportional, integral, and derivative gains (set unused gains to 0). st is the sample time in seconds (minimum 1). bias is the output value when the process variable exactly equals setpoint in a proportional-only loop. lo/hi are the output's low and high limits, and the trailing 0 is always present but unused.

2018 LOOP(0,RM100,HVALVE,HSETPT,PGAIN,0,0,1,5.5,3.0,9.0,0)

That official example drives a heating valve (HVALVE, output range 3.0-9.0) to hold room temperature (RM100) at setpoint (HSETPT) with proportional gain only (PGAIN) and no integral/derivative action, sampled every 1 second, biased to 5.5 at the valve's midpoint.

9. $LOC / $ARG -- local variables

$LOC and $ARG (optionally numbered, e.g. $LOC1) are scratch variables local to the program -- useful for temporary math or holding a value partway through a calculation, without needing a permanent database point for it.

10. DEFINE -- reusing one block of code across devices

Syntax: DEFINE(abbrev,string). abbrev is a short placeholder; string is the text (typically a long point-name prefix) it stands in for. Wherever you use the placeholder later in the program, it must be written surrounded by percent signs -- %abbrev% -- so PPCL knows to substitute it. This lets five identical AHUs share one block of control logic: rather than writing (or copy-pasting) five near-duplicate programs that differ only in their point names, each device's copy of the program carries its own DEFINE line mapping the same placeholder to that unit's real point prefix, and the logic below it stays identical.

01000 DEFINE(AHU,"BUILDING1.AHU01.") 01010 ON ("%AHU%SFAN")

Line 01010 is equivalent to writing ON ("BUILDING1.AHU01.SFAN") directly -- DEFINE runs once when the program is loaded onto the controller (it isn't part of normal line-by-line execution), and an abbreviation that starts with the letter C will fail to compile since a leading C marks a comment line. This trainer's scenarios don't require DEFINE -- every point name is spelled out in full so a scenario stays self-contained and checkable -- but it's worth knowing about since real multi-unit PPCL programs lean on it heavily to avoid maintaining the same logic in five different places.

11. Comments

A line starting with a bare C token is a comment -- often used as a header or label above a block of related logic, and completely ignored by the panel at runtime. Real PPCL programs typically open with one comment naming the whole program, then a comment ahead of each logical section.

01000 C --- CHLR CHILLER PLANT CONTROL PROGRAM --- 01010 C --- LEAD-LAG ROTATION LOGIC ---
